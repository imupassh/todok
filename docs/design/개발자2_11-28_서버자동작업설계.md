## 공통 원칙

- **멱등성**: 각 작업은 상태값(status)·타임스탬프를 조건에 넣어, 같은 행을 두 번 처리해도 결과가 같게 한다.
- **동시성**: 배치는 `SELECT ... FOR UPDATE SKIP LOCKED LIMIT N`으로 잠그고 처리 → 여러 워커·중복 틱에도 한 행을 한 번만 처리.
- **푸시**: 발송은 개발자 1 FCM 모듈 + `job_queue`(job_type=FCM_SEND) 이벤트 enqueue로 위임. 본 작업은 "언제 보낼지"만 결정.
- **S3 삭제**: 음성 파일 물리 삭제는 참조가 모두 사라졌을 때만. 즉시 지우지 않고 `job_queue`(S3_CLEANUP) 또는 개발자 1 S3 정리(매일)에 위임해 다른 참조(보낸 편지·북마크)를 깨지 않게 한다.
- **시각**: 모든 비교는 서버 `now()`(TIMESTAMPTZ) 기준.

## 작업 ① 편지 도착 처리 (이벤트성) — L-01·L-06·L-07

### 트리거
`POST /admin/reviews/{id}/approve`로 **편지(LETTER)가 승인**되는 순간. 승인 트랜잭션 안에서 함께 처리.

### 선행 조건 (L-04 반영)
- 승인 대상 편지의 `submitted_at ≤ letter_requests.expires_at`이면 마감 뒤라도 전달(계획서 가정).
- 대상 요청이 이미 하드 삭제(EXPIRED 7일 경과)됐으면 전달하지 않고 편지를 `WITHDRAWN` 처리(도착 불가 로그).

### 처리 순서 (단일 트랜잭션)
```
BEGIN;
-- 0) 멱등: 이미 PUBLISHED면 skip
SELECT status FROM letters WHERE id = :letterId FOR UPDATE;
IF status <> 'REVIEWING' THEN ROLLBACK; RETURN; END IF;

-- 1) 편지 전달 확정
UPDATE letters SET status='PUBLISHED', delivered_at=now() WHERE id=:letterId;

-- 2) 수신자 우체통 잠금 (5개 규칙 경쟁 방지)
--    recipient = 해당 요청의 requester_id
SELECT id FROM mailbox
  WHERE recipient_id=:recipientId AND status='UNREAD'
  ORDER BY created_at ASC FOR UPDATE;      -- 수신자의 UNREAD 집합 잠금

-- 3) 6번째 UNREAD 소각: 이미 5개면 가장 오래된 1개 삭제(하드)
IF (unread_count) >= 5 THEN
   DELETE FROM mailbox WHERE id = (가장 오래된 UNREAD id);   -- + S3_CLEANUP enqueue(참조 없을 때)
END IF;

-- 4) 도착 insert
INSERT INTO mailbox(recipient_id, letter_id, status, created_at)
  VALUES(:recipientId, :letterId, 'UNREAD', now());

-- 5) 요청 카운트(내부용)
UPDATE letter_requests SET letter_count = letter_count + 1 WHERE id=:requestId;
COMMIT;

-- 6) 커밋 후 푸시 enqueue
--    (a) 편지 도착 푸시 (L-01)  → job_queue FCM_SEND
--    (b) 새 UNREAD 개수가 '처음으로 5'가 되면 소각 알림 푸시 1회 (L-07)
```

### 5개 소각 규칙 상세 (L-07)
- 우체통 **안 읽은 편지 최대 5개 유지**. 6번째가 도착하는 순간 가장 오래된 UNREAD 1개 삭제(S3+DB).
- **소각 알림은 1회만**: UNREAD 수가 처음 5에 도달할 때만. 재발송 방지 플래그를 수신자 단위로 둔다 → `settings`가 아닌 사용자 상태(예: `notification_settings`에 `unread_full_notified_at` 또는 별도 플래그) 사용. **플래그 컬럼 위치는 개발자 1 `notification_settings`와 11/29 조율**.
- 읽으면(open) UNREAD→READ로 빠지므로, 다시 5에 도달하면 플래그 초기화 후 재알림 가능.

### 엣지 케이스
| 상황 | 처리 |
| --- | --- |
| 알림 비활성 사용자 | mailbox 처리는 그대로, 푸시만 skip(notification_settings.letter_enabled) |
| 동시 승인 2건 | 수신자 UNREAD FOR UPDATE로 직렬화, 5개 유지 보장 |
| 요청 이미 하드 삭제 | 전달 중단, 편지 WITHDRAWN + 운영 로그 |

## 작업 ② 열람 편지 24h 삭제 (주기성) — L-06·L-10

### 스케줄
주기 실행(예: 5~10분 간격, 확정은 운영). 기준: `mailbox.expires_at`(= opened_at + 24h).

### 대상/제외
- 대상: `status='READ'` AND `expires_at <= now()`.
- **제외: 북마크된 편지** — 같은 `recipient_id`+`letter_id`로 `letter_bookmarks`(direction=RECEIVED) 존재 시 삭제하지 않음(24h 지나도 보관, L-10).

### 쿼리 (배치, SKIP LOCKED)
```
WITH due AS (
  SELECT m.id, m.letter_id
  FROM mailbox m
  WHERE m.status='READ' AND m.expires_at <= now()
    AND NOT EXISTS (
      SELECT 1 FROM letter_bookmarks b
      WHERE b.user_id = m.recipient_id AND b.letter_id = m.letter_id
            AND b.direction='RECEIVED')
  ORDER BY m.expires_at
  FOR UPDATE SKIP LOCKED
  LIMIT 500
)
UPDATE mailbox SET status='EXPIRED', deleted_at=now()
WHERE id IN (SELECT id FROM due);
-- 삭제된 각 letter에 대해 S3 참조 점검 후 S3_CLEANUP enqueue(아래 참조 규칙)
```

### S3 음성 삭제 판단
한 편지의 음성은 **보낸 편지(sent-letters)·다른 참조**가 남아 있을 수 있으므로, mailbox 제거만으로 바로 지우지 않는다. `letters.status`가 WITHDRAWN이거나 어떤 mailbox/bookmark도 참조하지 않을 때만 S3 삭제(개발자 1 S3 정리 매일 배치와 규칙 공유).

### 북마크 해제 시
`DELETE /letters/{id}/bookmark` 후에는 일반 규칙 복귀 → 이미 24h 지났으면 다음 배치에서 정리.

## 작업 ③ 편지 요청 마감·0통 삭제 (주기성) — L-03·L-09 (+L-04)

### 스케줄
주기 실행. 기준: `letter_requests.expires_at`(= published_at + 24h).

### 상태 판정 로직
```
대상: status IN ('PUBLISHED','CLOSING') AND expires_at <= now()
각 요청 r 에 대해 (FOR UPDATE SKIP LOCKED):
  pending = COUNT(letters WHERE request_id=r AND status='REVIEWING'
                          AND submitted_at <= r.expires_at)   -- 마감 전 제출·검수중
  delivered = (r.letter_count > 0)  -- 전달된 편지 존재

  IF pending > 0 THEN
      r.status = 'CLOSING'          -- L-04: 마감 보류(검수 끝날 때까지 대기)
  ELIF delivered THEN
      r.status = 'CLOSED'           -- 1통 이상 → 정상 마감
  ELSE
      r.status = 'EXPIRED'; r.deleted_at = now()   -- L-09: 0통 → 소프트 삭제, 푸시 없음
  END IF
```

### L-04 마감 보류(CLOSING) 해소
- 마감 전에 제출돼 검수 중이던 편지가 **승인**되면 작업 ①이 전달 + `letter_count++`.
- 그 편지가 **승인/반려로 모두 처리**되어 `pending=0`이 되면, 다음 ③ 배치가 `CLOSING` → `delivered ? CLOSED : EXPIRED`로 확정.

### L-09 0통 처리 (가정)
- **푸시 없음**. `status='EXPIRED'` + `deleted_at` 기록 후 약 **7일 보관**.
- 보관 만료 하드 삭제(별도 패스):
```
DELETE FROM letter_requests
WHERE status='EXPIRED'
  AND deleted_at <= now() - (SELECT value::int FROM settings WHERE key='expired_request_retention_days') * INTERVAL '1 day';
```
- 앱 `GET /users/me/letter-requests`는 EXPIRED도 "사라짐" 상태로 표시 가능(실패 문구 금지, PRD).

### 엣지 케이스
| 상황 | 처리 |
| --- | --- |
| 마감 직전 제출 편지가 반려됨 | pending 감소 → 남은 전달분 유무로 CLOSED/EXPIRED |
| 게시 중 요청자 탈퇴 | 요청 즉시 EXPIRED 처리 + 관련 편지 전달 중단 |
| 배치 지연으로 24h 초과 | expires_at 기준이라 지연돼도 정확히 1회 확정(멱등) |
